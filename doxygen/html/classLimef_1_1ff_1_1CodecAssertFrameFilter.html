Detailed Description

FrameFilter that asserts the incoming stream matches an allowed codec pair.

On the first CodecFrame it inspects the video and audio codec IDs and checks them against a caller-supplied list of CodecPair values. If no pair matches the filter logs a fatal error and inutilizes itself: all subsequent frames (including the non-matching CodecFrame) are silently dropped.

When a pair matches, the CodecFrame and all following frames are forwarded downstream normally.

Why this matters per downstream destination

RTSP / RTP (RTSPMuxerFrameFilter)

The ffmpeg RTP muxer can packetize many codecs, but not all combinations have payload type assignments (RFC 3551 / RFC 5761). Common working pairs: H264+AAC, H264+MP3, H264+Opus, H265+AAC, VP8+Opus, VP9+Opus.

WebRTC (WebRTCMuxerFrameFilter)

WebRTC is extremely picky. RFC 8834 mandates Opus for audio and VP8/H264 as the minimum video codecs. AAC is not in the WebRTC spec and is not supported by browsers. G.711 (PCMU/PCMA) is mandatory but rarely used in practice. Allowed pairs: (H264|VP8|VP9|AV1) × (Opus|PCMU|PCMA).

Fragmented MP4 / browser MSE (FMP4FrameFilter)

Browser MSE for ISOBMFF is strict about codec support:

  • H264+AAC — universally supported (Chrome/Firefox/Safari/Edge)
  • H265+AAC — Safari desktop/iOS; Chrome behind a flag; Firefox: NO
  • AV1+Opus — Chrome 70+, Firefox 67+, Edge 79+; Safari: NO VP8/VP9 cannot be carried in fMP4 for MSE — use WebMFrameFilter instead.

WebM / browser MSE (WebMFrameFilter)

WebM only carries VP8, VP9, AV1 for video and Vorbis or Opus for audio. H264, H265, AAC, and MP3 are not valid in WebM.

Usage

CodecAssertFrameFilter assert_ff("assert", {
{AV_CODEC_ID_H264, AV_CODEC_ID_AAC},
{AV_CODEC_ID_H265, AV_CODEC_ID_AAC},
});
assert_ff.cc(downstream);
